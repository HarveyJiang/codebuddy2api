# 模型名去前缀：裸名自动选后端（设计方案，未实现）

> 状态：**方案讨论中**（2026-10-16）。用户提议：客户端只传 `kimi-k3`，系统按分配策略
> 自动路由到某个后端；用户侧永远只看到一个模型，不再需要 `trae/` 前缀。
> 本文档只做方案设计，**不实现**，待用户确认后再排 sprint。

---

## 1. 背景：前缀是给谁看的

今天的路由是「模型名即后端」（`specs/backend-isolation.md`）：

```
trae/<名>  → TraeBackend（字节）
其余（含 auto）→ WorkBuddyBackend（腾讯）
```

`trae/` 前缀的存在理由在代码注释里写得很清楚（`registry.py:backend_name_for`）：
Codex CLI / Claude Code 这类客户端**只能改 `model` 字段**，改不了 header 或路径，
所以前缀是「客户端零改造就能区分后端」的唯一硬信号。

前缀解决的是**路由歧义**问题。但它把本该由系统承担的复杂度推给了用户：
用户必须知道 `kimi-k3` 和 `trae/kimi-k3` 是两个东西、分别怎么收费、
分别在哪个后端可用。用户真正想要的是：**我就说 `kimi-k3`，你系统看着办**。

真实数据证实了这个诉求的合理性（`state.db`，46 个模型）：

| 裸名 | 腾讯侧 | 字节侧 |
|---|---|---|
| Kimi K3 | `kimi-k3-1`（1620000 micro） | `trae/kimi-k3`（1830000 micro） |
| Kimi K2.6/2.7 | `kimi-k2.7` / `kimi-k2.6` | `trae/kimi-k2.7-code` / `trae/kimi-k2.6` |
| Step-5 | `step-5-preview`（0.0） | `trae/step-5-preview`（0.48） |

注意两件事：**同名模型两边都有但 id 不完全一致**（`kimi-k3-1` vs `kimi-k3`），
而且**同名不代表同价**（Step-5 腾讯免费、字节 0.48）。这是整个方案里最危险的事实，
后面所有设计都是为了驯服它。

---

## 2. 核心事实：同名模型不是同一模型

在做任何「自动选」之前，必须先承认：`trae/kimi-k3` 和腾讯的 `kimi-k3-1` 只是
**名字像**，它们是两个上游、两套凭据、两套计费、两套可用性。任何把它们当成
「同一个模型的不同副本」来做轮转的方案，都是在撒谎。

这意味着「裸名自动选后端」**不是**负载均衡，而是**带策略的歧义消解**：
每次请求，系统要在候选后端里**选一个**，并为这次选择负责（可解释、可追踪、
可回滚）。选错了的代价是真实的：走错后端可能多花钱（0.0 vs 0.48）、
可能撞上冷却中的账号池、可能触发另一端的 kill switch。

---

## 3. 目标与非目标

**目标**

1. 客户端可以只传裸名（如 `kimi-k3`），系统按策略自动选一个后端执行，
   用户侧永远只看到一个模型。
2. 选择是**确定且可解释**的：同一次请求的落点可从日志复现（`request_logs.backend`
   已有该列，schema v8）。
3. `trae/<名>` 写法继续有效，语义变为**显式指定后端**（高级选项），
   不做任何迁移，现有客户端零改动。
4. 失败路径不比今天更差：选中的后端排队/冷却/禁用时，有明确的降级顺序，
   而不是静默失败或串到另一个后端乱试。

**非目标**

- 不做真正的「跨后端负载均衡」（按 QPS/延迟动态分流）。那需要健康度反馈环，
  是另一个量级的东西。
- 不合并计费：同名模型的两个后端版本继续按各自倍率记账（需求 1/8 的口径不变）。
- 不动账号层策略：账号池的轮转/随机/优先过期（`default_routing`）原样保留，
  本方案只解决「选后端」，选完后端之后还是老逻辑。

## 4. 用户侧契约

| 客户端写法 | 语义 |
|---|---|
| `kimi-k3`（裸名） | 「给我 Kimi K3，哪个后端**当前更合适**走哪个」。选择由第 5 节的策略决定，实际落点记入 `request_logs.backend`。 |
| `trae/kimi-k3`（带前缀） | 「明确要字节的 Kimi K3」。行为与今天完全一致，绕过自动选择。 |
| `auto` / 空 | 不变：走默认后端（今天是腾讯）。 |
| 裸名只在一个后端存在 | 直接走那个后端，**不触发任何策略**（退化为今天的行为）。 |

关键点：**裸名只在「多个后端都有同名模型」时才触发选择**。绝大多数模型
只存在于一边，方案对它们是零影响的——这保证了改动的爆炸半径最小。

「同名」的定义（用户已拍板用规范名映射，2026-10-16；必要性见下）：

| 字段 | 职责 | 可变吗 | 能当归一化键吗 |
|---|---|---|---|
| `model_id` | 上游原始字符串 + 对外路由键 | 否（动它断账本/客户端） | 否（`kimi-k3-1` vs `kimi-k3` 天然不等） |
| `name` | 展示名 | 是（用户可改名/添加时自填） | 否（无唯一约束，两边写法可能不同） |
| `canonical` | 归一化别名：分组 + 自动选择的键 | 由后端声明填写，用户一般不动 | **是** |

必要性（真实数据，`state.db` 46 模型）：Kimi K3 在腾讯叫 `kimi-k3-1`、
在字节叫 `trae/kimi-k3`——现有 `modelBaseName`（去前缀）分组把它们分成**两组**，
用户看到两行。`name` 碰巧都是 `Kimi-K3`，但它是展示文本不可靠。
没有独立的 `canonical` 列，这种跨后端别名永远合并不了。

填写规则：目录同步时由各后端声明自己的 `canonical_for` 映射，**只写非恒等的**
（用户拍板，2026-10-16）——即「只声明需要改名的」。默认值是「`model_id` 剥前缀即
规范名」，所以 Trae 的 `kimi-k3 → kimi-k3` 这种恒等映射**不写**，`canonical_for`
默认为空字典；只有腾讯需要写 `{"kimi-k3-1": "kimi-k3"}` 这类真正的改名。
少写恒等映射的理由：它没有信息量，却让每个新后端都要为自己的每个模型抄一遍
自己的 id，改上游 id 时反而多一处要同步的地方。

用户手工添加模型时可自填 `canonical`，留空即默认规则。

## 5. 选择策略：候选、排序、降级

一次裸名请求的处理分三步，每步的规则都必须是声明式的（延续第 3 阶段
「差异进声明」的传统，不能在 `resolve_backend` 里写 `if`）。

### 5.1 候选集

裸名 `M` 的候选后端 = 「目录里有规范名为 `M` 的**可用**模型」的后端集合。
「可用」指同时满足：

1. 后端**总闸启用**且**环境逃生门未关**（同一个 `is_enabled` 判定：设置页
   `settings.backend_enabled` 与 `CODEBUDDY_ENABLE_TRAE` 都为「开」才在候选里。
   总闸见 `backend-toggle.md`，是候选集规则的实现方）；
2. 该后端至少有一个启用账号（`has_enabled_account` 已有）；
3. 该后端的同名模型行 `enabled`（模型管理页的禁用开关继续有效）。

候选集为空 → 返回今天的 400（未知模型），错误信息列出「哪个后端因为什么出局」
（调试时最有用的信息，没有之一）。

### 5.2 排序（策略）

候选多于一个时，按策略排序。策略的粒度与候选项需要用户拍板（第 9 节），
候选实现（按推荐度排序）：

1. **静态优先级**（✅ 已选定，详见第 9 节第 2 条）：顺序 = **注册表顺序**，
   默认让腾讯在前（它是默认后端，`auto` 也走它，行为最可预测）。
   用户在设置页调序（覆盖成 `settings.model_backend_order`）。
   **不引入 `routing_priority` 数字字段**——注册表顺序本身就是后端对
   「我排第几」的声明（与第 3 阶段 `order` 字段同款），加数字字段等于同一件事
   声明两遍，迟早不一致。本质是「静态主备」——简单、可解释、零惊喜。
2. **按账号可用数**：哪个后端的可用账号多走哪个。动态，但「可用」的定义
   本身在变（冷却/排队/凭据失效），落点会抖。
3. **按剩余积分**：哪个后端剩得多走哪个。需要积分数据新鲜，而积分是按需刷新
   的（`credits_stale` 机制），用过期数据做路由决策是拿昨天的天气预报指导今天。

建议：**默认策略 1（静态优先级），2/3 作为后续可选策略**。理由见第 2 节：
这不是负载均衡，是歧义消解——可预测性比最优性重要得多。

### 5.3 失败处理：不跨后端重试（用户拍板，2026-10-16）

**一次请求只选一个后端**。策略排完序取第一名，剩下的候选**本次请求不再尝试**。
第一名走不通（账号全冷却、命中排队、上游 5xx）时，走**既有同后端降级逻辑**：
换号 → 同价格同类型换模型（`fallback_models`，现状），与今天完全一致。

原方案里「同一次请求内换下一个后端」的设计**作废**。理由（用户原话）：
切换逻辑不轮询后端；策略选好后端，调不通就走之前的逻辑（同价格同类型）。
跨后端重试会把「选后端」和「选账号/选模型」三层耦合在一起，
排障时说不清这次请求到底经历了什么。

直接后果（都是好消息）：

- **不变量 #5 维持不变**，不需要修订。`fallback_models` 不得跨后端，
  以前是什么以后还是什么，回归测试继续有效。
- 不需要 `route_trace` / `attempts` 字段。`request_logs.backend`（v8 已有）
  记唯一落点即可——一次请求只落一个后端，没什么可追溯的。
- 「降级上界」问题消失：上界恒为 1，不需要配置项。
- 排队降级顺序不变：同后端换号 → 同后端换模型（今天的两步）。
  「换后端」永远不在运行时发生，只发生在策略重排（调序/开关/账号启停）时。

### 5.4 大前提：单后端独立可运行（用户拍板，2026-10-16）

> 总体逻辑按**一个归属**来设计：先按只有 WorkBuddy 来设计，
> 后面只是增加了 Trae。即使把 Trae 模块下线，单独的 WorkBuddy 也能正常运行。

这是架构级原则，之前是事实（kill switch、懒构造、默认后端兜底），
现在明确为设计法：

1. **任何功能必须在只有默认后端时完整可用**。新功能不得假设第二个后端存在。
2. **下线一个后端 = 该后端相关行消失，其余一切不变**。总闸关掉（或环境变量关掉）
   Trae 后，裸名请求的候选集自然只剩腾讯，策略退化为「只有一个候选，直接走」——
   不需要任何特殊分支，这是 5.1 候选集定义的直接推论。
   （总闸的不变量是「启用集合恒 ≥ 1」，所以不会退化成「零候选」。）
3. **禁止为「多后端同时在线」写特殊逻辑**。本次否决的跨后端重试就是反例：
   它只在「恰好有两个后端且第一个挂了」时有意义，后端数量一变就得重写。
   策略排序 + 单后端降级与后端数量无关，2 个和 5 个同一个形状。

## 6. 数据模型改动

### 6.1 `models` 表：需要一个「规范名」列

今天 `models.model_id` 既是路由键又是展示键（`trae/kimi-k3` 二合一）。
新方案需要拆开：

- `model_id`：保持现状（带前缀的对外 id，路由键，不动——动它等于动所有外键与账本）。
- 新增 `canonical` 列（TEXT，可空）：规范名。目录同步时按第 4 节的规则填写；
  空 = 该行没有跨后端同名者（绝大多数行）。
- 查询「裸名 M 的候选」= `WHERE canonical = M OR (canonical IS NULL AND model_id = M)`。
  后半段覆盖「只有一个后端有、还没填规范名」的行，保证老数据零迁移。

迁移是加列（幂等，安全类型），与 v8/v9 同一风格。
> 版本号提醒：线上当前是 **v9**（`keys.last_used_at` 的 v10 尚未上线）。
> 归属方案先落（给 `models` 加 `backend`），路由方案后落（加 `canonical`），
> 两个迁移各自独立、版本号按实际落地顺序顺延。

**实现记录（2026-10-16，已完成——第一段「跨后端归并展示」）**

版本号最终是 **v14**（`_v13_to_v14`，见 `admin/db.py`）。落地时与文档有两处偏差，
都是刻意为之，记在这里免得下次照文档写错：

1. **`canonical` 是派生列，不由调用方传**。写入点 `db.save_models` 对每一行调用
   `registry.canonical_name(model_id)` 现算。理由：让调用方透传就会多出一条
   「persist 与注册表对同一模型算出不同值」的路径 —— 正是这一列要消灭的那类不一致。
   （`item.get("canonical")` 仍优先，留给测试与将来「用户手工指定别名」。）

2. **迁移不回填**，与本文档原先写的「同步时填写」一致，但读路径因此**不能**
   依赖列：`ModelRegistry.snapshot()` 用 `canonical_name()` 现算（内存态不查列），
   `save_models()` 才落库。所以「升级后到第一次同步之间」管理页也能正确归组，
   代价只是那段时间 DB 里的列是 NULL。

前端（`groupModelsByName`）从服务端返回的 `m.canonical` 直接归组，**不再自己算**。
这一条是实测教训换来的：第一版实现在前端按**展示名**归并，方向对但载体错 ——
`hy3` 与 `hy3-x` 展示名都叫「Hy3」却是两个真模型（倍率 0 vs 0.05），
按展示名合会把它们并成一个。规范名是**显式声明**的，不依赖「字符串规则碰巧对上」
也不依赖「展示名碰巧一样」。

声明位置（第 4 节的填写规则落地为代码）：

- `BackendSpec.canonical_for: dict`（`core/backends/base.py`）—— `{上游 id: 规范名}`，
  **只声明非恒等映射**。默认空字典 = 「剥前缀即规范名」。
- 腾讯侧实际只声明了一条：`{"kimi-k3-1": "kimi-k3"}`（`core/backends/workbuddy.py`）。
  字节侧 `canonical_for = {}`，因为它上游 id 与规范名恒等。
- 回归测试 `test_canonical_for_only_declares_non_identity_mappings` 拒绝显式恒等映射：
  它没有信息量，却让「加一个模型」变成「记得也来这里抄一遍 id」，抄漏不报错、
  只是静默不合组。

**本段只做了「归并展示」**。第 5 节的候选集/排序/降级（即「裸名自动选后端」的
路由部分）**尚未实现**，是 §8 的后续阶段。今天裸名请求仍只走默认后端。

### 6.2 `/v1/models` 去重规则

事实：`/v1/models` 今天**确实返回 `owned_by`**（`converter.py:list_models`），
但值是写死的 legacy 名字（`trae/` 开头 → `"trae-solo"`，其余 → `"codebuddy"`），
`created` 也是固定假时间戳。客户端理论上不需要关注它（OpenAI 协议里它只是
信息字段），实际影响限于部分客户端的分组展示。

去重规则（`owned_by` 写法一并定死，用户拍板方向，2026-10-16）：

- 同一规范名的多个后端版本 → 只返回**一条**，`id` 为裸名（如 `kimi-k3`），
  `owned_by` 写**当前策略第一名**。由于 5.3 已定「一次请求只选一个后端」，
  第一名 == 「这次传裸名实际会落到哪」（除非它挂了走降级——那是运行时，
  列表管不着）。诚实且稳定（静态优先级很少变）。
- 带前缀的显式 id（`trae/kimi-k3`）继续单独列出（高级用户可见），
  `owned_by` 保持今天的值。
- 客户端传裸名时，服务端按第 5 节选择；客户端传带前缀 id 时，直达。

去重只影响列表展示，不影响路由——路由看的是请求里的 `model` 字段。

> 附带发现：`list_models` 的 `m.startswith("trae/")` 是散落在 converter 里的
> 前缀硬编码（arch guard 只扫 `== "trae"` 比较与分派标识符，`startswith`
> 不在规则里）。实现本方案时顺手改成读声明（`prefix_for(m)` 非空即走该后端
> 的 `owned_by` 声明），并给 arch guard 加一条 `startswith("trae")` 规则。
> `BackendSpec` 为此需要新增 `owned_by` 声明（今天 `"trae-solo"` / `"codebuddy"`
> 是写死字符串）。
>
> **已完成（2026-10-16，`f5d3c01`）**：`owned_by` 声明**早就有了**
> （`trae-solo` / `codebuddy`），缺的只是「调用方用它」。已改为
> `spec_for(backend_name_for(m)).owned_by`。归并展示段（6.1）一并落了
> `models.backend` 列与 `canonical` 列，故 arch guard 的
> `startswith("trae")` 规则仍未加——那是独立的清理项。

### 6.3 账本与日志

- 成本账本以 `(account, model)` 为键（`model` 是实际执行的带前缀 id），**不动**。
  用户查账时看到的是真实发生的费用归属，这是对的——账本要记事实，不记意图。
- `request_logs` 已有 `backend` 列（v8），记本次请求的**唯一落点**——5.3 定死
  「一次请求只选一个后端」，所以这一列已经足够回答「这次走了哪个后端」。
- ~~新增 `route_trace` 记录候选集与选择过程~~ → **作废**（5.3 定死不跨后端重试，
  没有多次尝试可记）。选择过程的可解释性改用**不新增列**的办法：
  出错时（候选集为空）的 400 响应里逐个列出「哪个后端因为什么出局」——
  排障要的正是这条信息，而失败路径本来就要构造错误响应，边际成本近零。
  真要查历史为什么走某后端，看 `request_logs.backend` 即可。

## 7. 与现有机制的交互（逐条过）

| 机制 | 影响 | 处理 |
|---|---|---|
| 凭据一致性闸门（`_resolve_backend_or_http` 的 503） | 选择发生在闸门**之前**，闸门校验的是「最终选定的后端 vs 实际选到的账号」，逻辑不变 | 不动；但闸门触发时应提示「自动选择落到了 X 后端，而可用账号是 Y 后端」，否则用户看不懂 |
| 隔离不变量 #1–#4（选号过滤、try_select 透传、WAF 分桶、tick 兜底） | 全部按 `backend` 运作，新方案每次尝试都有明确的 `backend` | 不动；回归测试继续有效 |
| 隔离不变量 #5（降级不跨后端） | **无冲突**：5.3 定死「不跨后端重试」，反而正是 #5 要求的 | **维持不变**，回归测试继续有效 |
| 会话亲和（`request_affinity`） | 核实后**不需要改**（2026-10-16 修订）：哈希是 `sha256(caller, body["model"], identity)`，本就已含模型名；而裸名请求若某次落点变了，必然是策略重排或账号启停导致候选集变化，此时 `pool.select` 的 `bound in candidates` 校验会发现绑定的账号不在新候选里 → 自动重选并改绑，行为正确 | **不动**。把 backend 塞进哈希反而有害：每次策略重排都产生一个新亲和键，绑定表（上限 4096）被无意义地撑大 |
| 队列降级换模型（`fallback_models`） | 5.3 定死不跨后端 ⇒ 仍是「同后端换号 → 同后端换模型」两步，与今天一致 | **不动** |
| `/v1/models` 快照与前端模型管理 | 需求 8 的合并展示是前端做的；新方案要在 API 层去重（6.2） | 前端 `groupModelsByName` 逻辑可简化，但要保留带前缀行的展示 |
| 自动签到/积分刷新（`pool.tick`） | 按账号运作，与模型路由无关 | 不动 |
| 总闸开关（`settings.backend_enabled`） | 是候选集的第 1 条出局规则（5.1）；`backend-toggle.md` 已先行实现 | 候选集读同一个 `is_enabled`，不新增判定路径 |
| 环境逃生门（`CODEBUDDY_ENABLE_TRAE`） | 同上，优先级最高 | 不动 |

## 9. 决策记录（用户已拍板，2026-10-16）

1. **「同名」的判据**：✅ **引入规范名映射**。各后端声明 `canonical_for`
   （如腾讯声明 `kimi-k3-1 → kimi-k3`），不声明则默认 `model_id` 剥前缀即规范名。
2. **默认策略**：✅ **静态优先级**（用户拍板，2026-10-16）。默认顺序 = **注册表顺序**，
   腾讯在前（它是默认后端，`auto` 也走它，行为最可预测）。
   实现上**不需要 `routing_priority` 数字字段**——注册表顺序本身就是声明
   （`_REGISTRY` 表的排列即「每个后端声明自己排第几」，与第 3 阶段 `order` 字段同款）。
   用户在设置页调序 = 覆盖成 `settings.model_backend_order`（见第 4 条）。
   按账号数/按积分作为后续可选策略，不进首版。
3. **价格差的红线**：✅ **贵的方向要显式前缀**（用户拍板，2026-10-16 精确化）。
   自动选择只允许往便宜/同价方向切；免费变收费是不可接受的惊喜。
   精确定义（实现照抄，不留解释空间）：

   | 项 | 规则 |
   |---|---|
   | 数据源 | **`credits_micro`（整数）**，不用显示层的 `credits`（float）——用户明确要求「精确比较」，float 比较会引入误差 |
   | 比较基准 | **策略排序后第一个可用候选**（不是全部候选的最低价） |
   | 判据 | 候选的 `credits_micro` **高于**基准 → 该候选出局；**≤ 基准**（便宜或同价）→ 保留 |
   | `credits_micro` 为 NULL | **视为最贵**（等于 +∞）：只有显式前缀才能选中。「按标准计费」的模型不该被自动选中——那正是「免费变收费的惊喜」本身 |
   | 豁免一 | 请求带了显式前缀（`trae/xxx`）→ 整条规则跳过，那是用户自己的选择 |
   | 豁免二 | 用户**显式配置了顺序**（全局 `settings.model_backend_order` 或单 key `keys.model_backend_order` 非默认）→ 跳过，与第 4 条「知情选择」同一口径 |

   **边界情况（已定，写明免得实现时重新讨论）**：首选后端不可用（总闸关闭/
   无启用账号/模型被禁用）时，它本就不在候选集里，基准自动下移到下一个候选——
   不会把请求逼到「无解」。这符合「有得选就用」，也不构成惊喜（首选本来就不可用）。

   **诚实说明这条规则今天多为兜底**：当前策略是静态优先级，第一名恒为默认后端，
   便宜的候选本来也赢不了。所以它真正生效的场合是：
   (a) 将来加动态策略（按账号数/按积分）时，贵的后端可能排到前面；
   (b) 用户手动调序且**调成了非知情口径**的场景（豁免二之外）；
   (c) 自定义模型建出的倍率不一致行。
   留着它是因为它零成本，且在 a 场景上线前就能拦住。

   **实现前置**：`credits_micro` 今天**不在快照里**——`db.load_models` 读取时
   就用 `_from_micro` 转成了 float `credits`（`db.py:716`）。要让路由层做精确比较，
   必须把 `credits_micro` 一路保留到内存目录与 `snapshot()`（与需求 1 的
   「显示向下取整、DB 存精确值」共用同一个整数来源，不新增存储）。
4. **策略粒度**：✅ **全局默认 + 单 key 可配**（用户拍板，2026-10-16）。
   和现在**没有变化**——照抄 `keys.routing` 的现成模式：
   - 全局：`settings.model_backend_order`（JSON 有序列表，默认 = 注册表顺序），设置页调序；
   - 单 key：`keys.model_backend_order`（TEXT，NULL = 跟随全局，非空 = 自己的有序列表）；
   - 生效值解析照抄 `_routing_for` 的一行形状：
     `item.get("model_backend_order") or pool.model_backend_order`，未知后端名忽略。
   - 前端照抄 `routing-chip` 的 per-key 编辑入口。
   - 单 key 显式排序视为**知情选择**（与带前缀请求同级），不触发第 3 条的价格保护——
     配 key 的是管理员，看得见两边倍率。
   两处都是加列迁移（安全类型），与 `keys.routing` / `settings.default_routing`
   同一风格，不引入新机制。
5. **降级上界**：✅ **恒为 1，不跨后端重试**（用户拍板，2026-10-16）。
   策略选一个后端，失败走既有同后端降级。不变量 #5 维持不变，无需配置项。
6. **`/v1/models` 的 `owned_by`**：✅ **写当前策略第一名**（用户拍板方向，
   2026-10-16）。附带：`list_models` 的 `startswith("trae/")` 硬编码顺手声明化，
   并给 arch guard 加 `startswith` 规则；`BackendSpec` 新增 `owned_by` 声明。
7. **排期**：✅ **第三位**（用户拍板顺序，2026-10-16：总闸 → 归属 → 路由）。
   依赖链：`backend-toggle.md`（候选集第 1 条读它）→ `model-backend-attribution.md`
   （`backend` 列 + 多行结构是候选的原料）→ 本方案。
   另外**不与其它后端接入（如 Qwen）并行**——新后端接入会新增候选维度，
   两个变量一起动不好验证。

## 附：为什么不是「纯分配策略、不保留前缀」

用户原话是「没必要加前缀前置区分，后端根据策略来使用」。本方案保留前缀作为
显式指定，是出于三条硬理由：

1. **排障需要确定性入口**。自动选择出问题时（比如某后端 silently 降质），
   用户/运维需要一种方式说「这次强制走字节」。没有前缀，这个入口就不存在，
   只能去改策略配置——动全局配置去排障一次个案，是反模式。
2. **价格差需要用户知情同意**。0.0 vs 0.48 的例子说明「自动选」可能替用户
   花钱。显式前缀是用户说「我知道这边的价格，我就要这边」的唯一方式。
3. **零迁移**。现有客户端（已经写死 `trae/xxx` 的）一行不用改。
   去掉前缀是破坏性变更，保留前缀是纯加法。
