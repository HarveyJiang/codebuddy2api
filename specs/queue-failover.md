# 容量队列自动切换 Spec：命中排队时换号 / 降级模型重试

> 状态：已实现（2026-10-15）。**默认关闭**（`queue_failover=false`），后台「账号池设置」手动开启。
> 实现见 `admin/pool.py`（`is_queue_error` / `mark_queued` / `fallback_models` / `PoolMiddleware._attempt`）、
> `admin/db.py`（schema v4）、`admin/server.py`、`admin/static/`。
> 基线 commit `0b44a49`。

---

## 1. 背景：这是什么错误

免费模型在高峰期会被上游放进 **Capacity Queue（容量队列）**，请求不立即处理，而是返回：

```json
{
  "code": "WAITING",
  "model": "Step-5-Preview",
  "message": "当前模型资源紧张，请等候。Step-5-Preview 前方约 7859 位用户排队，升级会员可享受更快速服务 升级后请重新发送当前任务以享受优先通道。",
  "data": { "queue_position": 7859, "queue_size": …, "estimated_wait": …, "retry_after": … }
}
```

要点（来自客户端逆向，见 issue 讨论）：

- 文案是**服务端下发的** `message`，客户端原样展示；客户端包里搜不到这些字。
- 状态是**结构化的**：`code` 取 `WAITING` / `FULL` / `USER_LIMIT`，客户端按 `isCapacityQueueErrorCode(e.code)` 判定，并按 `data.retry_after` 轮询。
- 桌面端自己会轮询等待；**网关不能干等**——我们面对的是 API 客户端，等下去只会让它挂住。

`USER_LIMIT`（个人额度到顶）**不在**本次可切换范围：换号或换模型都救不了额度，必须让用户看到。

---

## 2. 现状与问题

当前代码**完全不识别排队**（`grep WAITING` 为空）。后果：

1. 排队文案原样透给客户端，看起来像一次正常的模型回答。
2. 账号池不知道这个号刚排过队，**下一次请求大概率还选它**，继续排队。
3. 免费模型高峰期几乎不可用。

历史上曾实现过排队切号（`89712f5`），但在 `4a417fc` 被 revert：**扣留响应头等待排队判定时，管理 API 与 `/health` 全部超时、healthcheck 持续失败**。

复盘那次事故，根因是**扣留没有上界**：一旦上游不发首包（卡死、慢排队），中间件就无限期停在那里，而 `PoolMiddleware` 是所有请求（含 `/health`）的必经之路。本 spec 的实现必须堵死这一点。

---

## 3. 目标与非目标

**目标**

1. 命中容量队列时，在**尚未向客户端发出任何字节**的前提下，自动换一个账号重试。
2. 换号仍排队时，**降级到同价位的免费模型**再试；仍不行则退到 `fast-model` 智能路由兜底。
3. 全程对客户端透明：成功时它只会看到一次正常回答。
4. 让位有记忆：排过队的账号短期不再被选中，避免反复撞墙。

**非目标**

- 不改客户端、不改上游协议，不做「屏蔽提示文案」这类表面处理。
- 不处理 `USER_LIMIT`（额度问题换号无意义）。
- 不引入总超时：长推理、长输出的正常流不受影响（与 `stream-robustness.md` 一致）。

---

## 4. 关键设计决策

### 4.1 扣留必须有硬上界（事故防线）

中间件扣留 `http.response.start` 的时长受 `queue_hold_ms` 约束（默认 `3000`ms）：

- **首包在窗口内到达** → 立刻判定，正常流直接放行（`emitted=True`，之后永不扣留）。
- **窗口内没有任何 body** → 认定「不是排队，是上游慢」，立刻把 start 放行给客户端，本次**不切号**，回到原有行为。
- **任何异常路径** → `finally` 保证补发完整的 `start` + `body`，绝不让 ASGI 出现「callable returned without completing response」。

这条是整个改动的地基：**没有上界就没有扣留权**。原来的实现缺的就是它。

### 4.2 判定只看首包，且要求「无内容」

排队错误的特征是「第一个分片就是完整的小 JSON/SSE 错误帧，且不含 choices/delta」。因此：

- 只有在**首包**（`emitted=False`）时判定；
- 命中 `queue` 还需 **`has_content=False`**——一旦响应里出现真实内容，立即放行走原路，绝不重放（重放会导致客户端收到重复输出）。

### 4.3 形态全兼容

用户确认「不确定上游是 200+SSE 还是非 200」，所以判定**同时接受**：

| 载体 | 判定 |
| --- | --- |
| HTTP 状态码 | `429`、`503` 视为排队 |
| body `error.code` / 顶层 `code` | 字符串 `WAITING` / `FULL` / `QUEUE` / `BUSY`，或数字 `11102`/`11103`/`11001`/`50001`/`429`/`503` |
| body 文案 | 关键词兜底：`当前模型资源紧张`、`前方约`、`位用户排队`、`优先通道`、`retry_after` 等 |

`USER_LIMIT`、（若出现的）`11101` 明确**排除**。关键词是兜底而非主判据，避免上游文案微调就失效。

### 4.4 换号与降级模型是一个循环里的两条腿

单次请求最多尝试 `queue_retry` 次（默认 3）。每次尝试的**决策顺序**：

1. **先换号、不换模型**：同模型换个账号，可能就不排队了（免费模型排队是账号/时段相关）。
2. **账号换不动了**（候选耗尽或已试过）→ **降级模型**：在同价位段里挑一个没排过队的免费模型。
3. 同价位段也试完 → 退到 `fast-model`（智能路由，官方固定提供，不参与 cli 菜单排队）。
4. 仍失败 → **把上游原始排队响应原样返回给客户端**（保留 `message` 与 `data.retry_after`，让客户端自己决定轮询）。

### 4.5 降级目标的选取规则

「同价位免费模型」的定义与排序：

- 只取 `enabled`（未被用户在管理页禁用）且**可调用**的模型（`models` 表语义：可调用性只由 `enabled` 决定，与上游是否返回无关）。
- **同价位**：以当前请求模型的 `credits` 为基准，取 `credits` 落在同档的模型。档位用相对区间判定（±50%）而不是精确相等，因为上游倍率是离散但并不整齐的小数。
- 结果按 `credits` **升序**（越省越好），已排过队/已试过的排除。
- 兜底 `fast-model` **不参与**上面的排序，它只在最后被附加一次。

### 4.6 让位而非硬冷却

命中排队的账号记 `queued_until = now + queue_cooldown`（默认 120 秒）：

- `select()` 优先挑选 `queued_until` 已过期的账号；**全部都在排队期内时忽略该标记**（避免自我封锁成 503）。
- 让位**不**计入 `consecutive_fails` 退避，也不用 `cooldown_until`（那是认证/限流的硬冷却，语义不同）。
- 让位状态落库（`account_status.queued_until`），重启保留。

### 4.7 与 stream-robustness 的关系

本功能**不**改变空闲超时语义。扣留窗口（秒级）远小于 `stream_idle_timeout`（默认 120 秒），两者不冲突：窗口只管「首包来之前」，空闲超时只管「分片之间」。

## 5. 配置

新增 `pool` 设置项（后台「账号池设置」页），全部落 SQLite `settings` 表：

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| `queue_failover` | `false` | 总开关。**默认关闭** |
| `queue_retry` | `3` | 单次请求最多尝试几次（含首次），1 = 不重试 |
| `queue_cooldown` | `120` | 命中排队的账号让位秒数 |
| `queue_hold_ms` | `3000` | 扣留首包的硬上限（毫秒），同时也是事故防线 |
| `queue_model_fallback` | `true` | 换号用尽后是否降级模型 |
| `queue_fallback_model` | `fast-model` | 最后的兜底模型 |

非法值一律 400 拒绝（与既有设置项的校验风格一致）。

---

## 6. 可观测性

- 每次切号/降级 `_logger.info` 一行：`账号 <id> 命中容量队列（WAITING），让位 120 秒，改为尝试 <model>`。
- 请求日志（`request_logs`）沿用现有链路：切号成功后只记一条成功记录，`account_id` 是**最终生效**的账号——不把中间失败的账号记成请求账号。
- 中间失败的账号不计入 `request_count` 的「成功」，但让位状态可从管理页账号行看到（`last_error` 写「上游排队，已让位 N 秒」）。

## 7. 测试

`tests/pool/test_account_pool.py` 补：

- `WAITING`（字符串 code）与非 200 `429`/`503` 两种形态都判定为排队。
- `USER_LIMIT` **不**判定为排队。
- 首包窗口超时（上游不发 body）时**不切号**，且响应仍完整发回客户端（事故回归测试）。
- 首包已含内容时即使命中排队关键词也**不**重放。
- 切号成功后响应只出现一次，`account_id` 为最终账号。
- 降级模型的选择顺序：同价位免费模型升序 → `fast-model` 兜底。
- 全部账号都在让位期内时 `select()` 仍能返回账号（不自锁成 503）。
- 开关关闭时行为与改动前完全一致（默认关闭的回归保障）。
