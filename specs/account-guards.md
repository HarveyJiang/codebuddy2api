# 账号限额护栏与轮转退避

两个独立的保护机制，都在**请求路径**上生效，都默认**无为**（不改变现有行为）。
护栏拦住会把账号烧穿的请求；轮转退避与 WAF fail-fast 让「换号重试」这个动作本身
不再成为新的风险来源。

来源：GitHub 上 `KeyPort`（Python 分支）的 `pool/guards.py` 与 `upstream/rotateguard.py`。
只迁移了语义，实现按本项目的既有结构重写。

---

## 零、关于「要不要继续从 KeyPort 抄」——已调研，结论是不抄

`KeyPort` 剩余的功能（captcha 农场、旅行/任务/试用奖励领取、激活遥测）**全部建立在
ZCode / z.ai 的 API 上**，与本项目的上游腾讯 CodeBuddy 不是同一套服务。逐项对应：

| KeyPort 功能 | 它依赖的端点 | 归属 |
|---|---|---|
| captcha 农场 | `zcode.z.ai` 的 `X-Aliyun-Captcha-Verify-Param`（阿里云无痕验证） | z.ai |
| 奖励领取 | `{plan_base}/billing/preview` + `billing/claim` | z.ai 的套餐系统 |
| 激活遥测 | `/api/v1/client/configs`、`/api/v1/event/report`（免鉴权） | z.ai |
| **本项目上游** | `copilot.tencent.com`、`www.codebuddy.cn/v2/billing/meter/` | 腾讯 CodeBuddy |

判定依据（可复核）：

1. 本仓库全局搜 `captcha` / `X-Aliyun` / `verifyParam` **零命中**——我们从未给上游
   发过验证码参数，上游也从未索要。
2. captcha 模块的注释自己写明：参数**一次性**、连缓存 45 秒都在其环境下失效。
   这是端点行为，换上游即无意义。
3. 奖励领取的资格判据是 z.ai 自己的激活遥测，其文档写明「激活上报必须先于 preview，
   否则形成 preview 恒空 → 永不激活的死锁」。这套状态机只在 z.ai 上有意义。
4. 另外两个**确实**基于腾讯 CodeBuddy 的参考实现（`Sliverkiss/CodeBuddy2api`、
   `orangeboyChen/codebuddy2api`）经查**都没有**任何签到 / 领取 / 奖励自动化代码。

因此本项目上游侧唯一的自动化就是**签到**（`daily-checkin` +
`checkin-activity-status`，见 `AccountPool.operate`）。要新增奖励类功能，必须先证明
腾讯这边存在对应端点——**不要照抄 z.ai 的接口名**，那只会产生永远 404 的废代码。

## 一、账号限额护栏（`admin/guards.py`）

### 为什么需要

上游只告诉你「余额还剩多少」，**不会阻止你把余额用尽**。把账号烧穿会触发上游的
提醒甚至风控，而这是可以完全在本地避免的。

### 四条护栏

| 护栏 | 触发后行为 | 防的是什么 |
|---|---|---|
| `guard_reserve_credits` | 账号整体不再接单 | 余额被用尽后触发上游提醒 / 风控 |
| `guard_daily_token_limit` | 账号整体不再接单 | 单账号一天吃掉过多 token |
| `guard_daily_credit_limit` | 账号**只服务免费模型** | 付费模型把当天积分额度烧光 |
| `guard_model_daily_token_limit` | 该账号**仅该模型**不再接单 | 单账号单模型撞上游 24h 窗口配额 |

### 三条不可动摇的语义

1. **`0` = 关闭，默认全关。** 护栏会主动拒绝请求，是「替用户做决定」的功能。
   默认值必须是无为，否则升级就会悄悄改变线上行为、甚至把账号池停掉。
   所有护栏关闭时，`_apply_guards()` 直接返回原候选列表，**一次库都不查**。

2. **计数未知时绝不停用。** 用量读不出来（库异常、还没聚合过）时计数是 `None`，
   护栏**放行**而不是停用。宁可放过一次请求，也不能因为读不到数据把整个账号池
   判死——那比被烧穿严重得多。`DailyUsageCache.get()` 把 loader 抛出的异常
   **吞掉并返回 `None`**，就是为了让这条语义无法被绕过。

3. **按本地 0 点解封**（北京时间），与上游的日窗口一致。护栏只在请求路径生效，
   定时任务（签到 / 保活 / 领取）**不受影响**——任务本身不消耗对话额度，
   被护栏挡住只会白丢功能。

### 免费 / 付费怎么判

判据是**实测成本账本**（`admin/cost_ledger.py`）：账本认为该账号跑该模型免费，
才算免费。账本没观测过的模型一律按**付费**处理——「不确定是否免费」不该被当作
免费放行，否则 `daily_credit_limit` 形同虚设。

### 计数从哪来

新增 `account_usage_daily` 表（schema v6），按 `(account_id, day, model)` 累加：

```
INSERT ... ON CONFLICT(account_id, day, model) DO UPDATE SET
  count = count + 1,
  tokens = tokens + excluded.tokens,
  credits_micro = credits_micro + excluded.credits_micro
```

几个刻意的选择：

- **累加而非快照覆盖**。与 `key_usage_daily` 不同——那个写的是「当日累计快照」
  （`keys.usage` 本身是内存里的当日累计值），而这个表的写入粒度是**一次请求**，
  没有快照可覆盖。因此重启后内存计数丢失也无妨：库里已经逐次累加过了，
  这正是把计数放库里的原因。
- **按 `(账号, 天, 模型)` 三元组建主键**，一次覆盖三种查询（账号总量、账号当日
  积分、账号单模型 token），不必建第二张表。
- **credit 按 MICRO 落库**，与其他金额列一致，避免浮点累加漂移。
- **`request_logs` 聚合不出来**：它只有状态与耗时，没有 token / credit 列。
- 保留 `KEY_USAGE_KEEP_DAYS` 天，启动时裁剪。

护栏关闭时 `note_usage()` 直接返回，**不写库**——默认配置下不产生任何额外写入。
护栏开启时每次记完账立刻 `invalidate()` 缓存，否则刚用完额度的号在 TTL 内仍会被
判为可用。

### 全部候选被挡下时说什么

不改写成「暂无可用账号」。护栏挡下的号**仍然是可用账号**，上报「账号已达本地限额」
比上报「请检查暂停、积分、冷却或登录状态」有用得多——后者会让人去查登录态，
方向完全是错的。

## 二、轮转退避与 WAF IP 级 fail-fast（`admin/rotation.py`）

### 为什么轮转换号要加抖动

换号之间零间隔本身就是可被统计的节奏特征：上游看到的是「一个出口 IP 在几十毫秒内
用不同身份连续发请求」。但**固定周期**退避同样不行——多个客户端请求会在同一时刻
失败、同一时刻重试，**再次聚团**，而 WAF 的频控恰恰按密度判罚。所以退避必须带
抖动打散相位。

形态：`BACKOFF_BASE = 0.5s`，`base · 2ⁿ` 封顶 `BACKOFF_CAP = 8s`，再施加
`JITTER_FRACTION = ±25%` 的均匀抖动。轮转次数本身有上限（`queue_retry`，默认 3），
实际等待序列只有 500ms / 1s 两级；封顶只是防御性约束。

### 为什么需要 IP 级 fail-fast

`403` 有时拦的是**网关的出口 IP**，而不是某个账号。这种情况账号级软冷却不够：
轮转会继续拿别的号打同一个 IP，把一次客户端请求**放大成 N 次上游请求**，
越转越糟。

本项目已知的 `11128`（`Illegal API invocation from an unapproved channel`）
就是这类——实测换遍全池 8 个账号全被拦，与账号无关。

### 判定口径：数「不同账号」，不是数「失败次数」

```
短窗（60s）内不同账号命中 WAF 数 ≥ 2  →  判为 IP 级，激活 60s
```

刻意选这个口径的理由：

- **单号反复 403 属账号自己的偶发问题**，归账号级软冷却管，不该停掉整个池子的
  轮转。取阈值 1 会把任何单号的偶发 403 误判成 IP 被封——那比问题本身更糟。
- **两个不同号在 60 秒内接连被拦**，就只能是出口 IP 层面的问题了。
- **同一个账号重复命中只覆盖时间、不增加计数**，因为口径是「有几个不同的号被打」
  而不是「被打了几次」。

### 激活期语义

- **激活期内不续期、不记账**。自然解除即可，不必因为持续有拦截就把封锁无限延长
  ——那会让一次误判变成长期停摆。
- **激活时清空窗口**：解除后需要全新的一批命中才能再次判定，不会拿旧账立刻重新触发。
- **进程内状态，重启清零**。窗口只有 60 秒，重建成本极低；落库反而会带来
  「重启后继承一个可能早已过期的封锁」的风险。

### 与账号级冷却的关系

协同、不叠加。账号级状态照常记账（该冷却的号照常冷却，403 仍走 5 分钟本地退避），
IP 级状态只回答一个问题：**这一轮还要不要继续换号**。

### 在哪判定

- **排队路径**（`kind="queue"`，会轮转）：判定后若激活立刻 `break`，不再换号。
  这是 gate 真正起作用的地方。
- **收工路径**（`kind="done"`，含 403 / 11128）：也要判定并记账，否则这条线索
  整个丢掉。`done` 本身不轮转，所以这里只影响后续请求的判定窗口。

> 注意：`403` 在当前架构下走 `kind="done"`，**本来就不会轮转**（它直接冷却账号并
> 把响应透传给客户端）。所以 gate 对它的价值是「记账 + 影响后续窗口」，而不是
> 「阻止本次放大」。

## 相关设置

设置页「账号限额护栏」分组，四项全部 `0` = 关闭。设置随 `overview.pool` 下发，
分组口径由后端 `AccountPool.SETTING_GROUPS["guards"]` 给出，避免前后端两套。

`overview.metrics.waf_gate` 透出当前 gate 状态（是否激活、还剩多久、窗口内有几个号），
用于判断这套机制有没有在起作用。
