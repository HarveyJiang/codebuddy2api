# 后端总闸：设置页启用/禁用后端（设计方案，未实现）

> 状态：**方案讨论中**（2026-10-16）。用户需求：设置页可勾选启用/禁用
> workbuddy / trae；禁用某个后端后相关功能全部消失，但数据库保留，
> 重新启用即恢复；API key 相关的账号/模型选择不可用禁用后端的东西。
> 本文档只做方案设计，**不实现**。

---

## 1. 这是「大前提」的用户侧落地

`model-routing-by-policy.md` §5.4 定了大前提：按单后端可独立运行设计，
Trae 下线不影响 WorkBuddy。本方案就是把这句话做成用户手里的开关：
**总闸是「下线某个后端」的官方动作**，与 `CODEBUDDY_ENABLE_TRAE` 环境逃生门
语义一致，只是从运维手段变成设置页功能，且两个后端都有（不止 Trae）。

## 2. 语义表：禁用后端 X 后每一处的行为

| # | 路径 | 禁用后行为 | 现状 |
|---|---|---|---|
| 1 | 设置页 | 每个后端一行总闸（checkbox，注册表驱动，加后端自动多一行） | 无，需新增 |
| 2 | 请求路由 | 带 X 前缀的请求 400（明确报错，不静默换后端） | 已有（`resolve_backend`） |
| 3 | 模型列表/快照 | X 的行不显示 | 已有（`snapshot`/`enabled_models` 跳过） |
| 4 | 目录拉取 | 跳过 X（`fetch`/`refresh_catalog`/后台定时都不打 X 的上游） | **缺口**：现状照拉 |
| 5 | 数据库 | X 的行**保留**（`available` 不动），启用后原样恢复显示 | 已有行为，保持 |
| 6 | 账号池选号 | X 的账号不参与任何选号（含排队重试、亲和绑定） | 部分：路由层 400 挡住了请求，但选号函数本身不查开关 |
| 7 | 自动签到/积分刷新 | X 的账号跳过（不打 X 的上游） | **缺口**：`tick` 只按账号 backend 挑，不查开关 |
| 8 | API key 绑定 | 可用模型/账号选择器中 X 的项置灰不可选；已绑了 X 的 key，其请求按「无可用账号/模型」正常报错（400/503），**不串到别的后端** | **缺口**：选择器不过滤 |
| 9 | 前端 | 后端相关入口（登录方式按钮、目录刷新按钮）按开关隐藏 | 部分：登录按钮已按 `login_kind` 渲染，需加开关条件 |

第 8 条的后半句是关键：已绑定的 key 在后端被禁用后，**报错而不串**。
串到别的后端是隔离不变量要杀的头号行为，报错才是对的。

## 3. 开关存哪：`settings` 加 JSON 列（用户拍板，2026-10-16）

原方案写「不能进 `settings` 固定列，要建新表」——**这个判断不精确，收回**。
v9 的真实教训是「**不能动态发明列名**」（当时第一版写成
`models_updated_<backend>`，启动报 `no such column: models_updated_trae`
直接挂掉 `create_app`）；但一个**固定名字、内容按后端伸缩**的 JSON 列，
根本不会触发这个问题。而且：

- 先例：`keys.models` / `keys.accounts` 就是 JSON 数组存 TEXT；
- 成本：`save_settings` 本来就是整行重写（全列 `INSERT OR REPLACE`），
  JSON 读改写不增加任何额外开销；
- 读取：`get_settings` 整行读进内存，`is_enabled` 在内存里查 map，
  不需要 SQL 按后端过滤——「SQL 查不方便」不是问题，因为没人这么查。

最终形状（两列，各管一个概念，与 `SETTINGS_COLUMNS` 一列一概念的风格一致）：

- `backend_enabled TEXT NOT NULL DEFAULT '{}'` — `{后端名: 是否启用}`，
  缺键即启用（新后端零迁移，加行不加列）；
- `model_backend_order TEXT NOT NULL DEFAULT '[]'` — 全局后端顺序（有序列表），
  空即注册表顺序（裸名自动选后端方案用，见 `model-routing-by-policy.md` §9.4）。

与环境变量的关系不变：`CODEBUDDY_ENABLE_TRAE=0` 保留为**最高优先级逃生门**
（运维用，不经过 UI）；`is_enabled(name)` = 环境未禁用 **且** map 中未禁用。

## 4. 禁用任一后端都是对称的（2026-10-16 修订）

原方案写「关掉 WorkBuddy 会有特殊后果（裸名 400、排队兜底失效）」——**结论作废**。
那是把注册表里的「默认后端」（`default_for_missing_backend`，给无归属字符串兜底的
**默认值**）误当成了「主干/本体」。核实现状后：

**裸名 400 与关哪个后端无关。** `resolve_backend` 对带前缀请求查
`is_enabled(名字)`：关掉 Trae，`trae/xxx` 请求同样 400。两个后端对称，
不存在「关腾讯才有的后果」。

**排队兜底不依赖默认后端。** `admin/pool.py` 的 `same_backend(entry)` 比的是
**本次请求落到的那个后端**（`entry.get("backend", default_backend()) == backend`），
不是 `_default`。所以请求落到 Trae 时，兜底候选从 **Trae 自己的目录**里挑同价同档，
Trae 的模型就能当兜底——不存在「兜底失效」。
唯一会跳过的是设置里**手工写死**的 `queue_fallback_model`（默认值 `fast-model`
恰是腾讯私有档），只有它跨后端时会被跳过——那是「兜底模型配错了」，
且是 §5.3「不跨后端」**要求**的行为，不是关后端的必然后果。

**裸名的去向由策略决定，不是「必然落到默认后端」。** 策略在**启用的后端集合**
里排序选第一名（`model-routing-by-policy.md` §5）；启用集合只剩一个时直接用它。
这正是 §5.4「下线一个后端 = 相关行消失，候选集自然退化，无需特殊分支」。

### 修订后的语义（对称）

| 场景 | 行为 |
|---|---|
| 关掉 X | X 的模型/账号/目录/签到不可见不参与；带 `X/` 前缀请求 400（明确报错，不静默换后端） |
| 裸名请求 | 策略从**启用集合**里选第一名；只剩一个后端时即用它 |
| 排队降级 | 仍在**本次请求落到的后端**内换号 → 同价同档换模型；后端有几个不影响 |
| 两个后端都关 | 所有请求 400（无路由目标）——所有后端共同的后果，非某后端专属 |
| 数据库 | 一律保留，重新启用即恢复 |

### 附带约束：`default_for_missing_backend` 与总闸无关

`default_name()` 在一个默认后端都挑不出时抛 `RuntimeError`（`registry.py`）。
这条约束针对**代码声明**（注册表里恰好一个后端声明它，
`test_at_most_one_default_backend` 守着），**不随运行时开关变化**——
用户关掉默认后端不等于「没有默认后端」（声明还在，只是运行时不参与候选）。
总闸只管运行时可见性，不碰声明层。

**因此 UI 不需要针对某个后端写特殊警告**；只在「两个都关」时提示无可用后端。

## 5. 改动清单（预估，实现时用）

| 位置 | 改动 |
|---|---|
| `admin/db.py` | 新表 `backend_flags` + 读写方法；迁移（建表，无回填，缺行即启用） |
| `core/backends/registry.py` | `is_enabled` 同时读表（需把 Store/DB 引用传进去或回调注入——registry 目前不依赖 admin 层，**不能顶部 import**，用回调参数或懒引用） |
| `admin/models.py` | `fetch`/`refresh_catalog` 跳过禁用后端 |
| `admin/pool.py` | `tick` 的签到/刷新候选过滤禁用后端账号 |
| `admin/server.py` | key 绑定选择接口过滤；设置页读写总闸的 API |
| `admin/static/*` | 设置页总闸卡片 + key 绑定选择器置灰 + 相关入口按开关隐藏 |
| `tests/` | 每条语义的回归测试（禁用→行为消失→启用→恢复），arch guard 不变 |

注意 `registry.py` 不能 import `admin`（循环依赖：admin 依赖 registry）。
`is_enabled` 读表需要一个注入点——设计时可参考 `set_catalog_provider` 的
「admin 启动时注入」模式（Trae 目录提供者就是这么解的，有先例）。

## 6. 开放问题

   前提（候选集/分组/拉取都要读它），且独立可上线。
2. **key 已绑禁用后端时的错误文案**：要不要明确告诉客户端「该后端已被管理员禁用」？
   建议要（排障时最有用的信息），但文案待定。
3. **审计**：开关切换是否记一条事件（`events`）？建议记——「谁什么时候关了 Trae」
   是线上排障的高频问题。
