# 密钥「最后使用」时间（设计方案，待确认）

> 状态：**已实现**（2026-10-16）。本文档是 `keys.last_used_at` 的设计与实现记录。
>
> 上一版做过一次（未提交、已 revert），本次重做，见 §6「上一版的问题」。

## 1. 要解决的问题

密钥列表现在只有「今日用量」，看不出**这个密钥还在不在用**。管理员的典型问题是：

- 这个 key 还有客户端在连吗？还是三个月前的遗留物，可以删了？
- 我刚配的 key 为什么一直不工作？（配错了：模型白名单没包含目标模型 / 账号全被冷却 /
  后端被禁用 —— 这些请求全部失败，但 key 本身在**被高频调用**）

第二个问题正是当前 UI 的盲区：今天用量那列会涨（因为失败路径也记账），但看不出
「最后一次成功是什么时候」还是「一直在失败」。

## 2. 语义定义

**`last_used_at` = 该密钥最后一次「通过鉴权且未超配额」的时刻（秒级 Unix 时间戳）。**

这句话里每个限定词都有用：

| 情况 | 算不算「使用」 | 理由 |
|---|---|---|
| 请求正常完成 | ✅ | |
| 上游 5xx / 冷却 / WAF 拦截（有响应） | ✅ | 请求打到了服务，key 在被用 |
| **无可用账号 → 503** | ✅ | key 在被高频调用，但账号全不可用 —— **最该被发现的坏配置** |
| **模型不在白名单 → 403** | ✅ | 同上，配错了 |
| **后端/模型被管理员禁用 → 400** | ✅ | 同上 |
| 请求体超限 → 413 | ✅ | 同上 |
| **超出每日限额 → 429** | ❌ | 请求没真正用掉服务。管理员问的是「最后一次真的用上」 |
| 密钥不存在 / 已撤销 / 已过期 → 401 | ❌ | 没通过鉴权 |
| 密钥错配（前缀不符） | ❌ | 没通过鉴权 |

**关键判断**：把 503/403/400 算作「使用」，是因为这些场景下用户正在狂打一个
配错的 key —— 正是最需要被界面暴露出来的。如果只在「真正打到上游」时记录，
这类 key 会显示成「从未使用」，**比没有这列更误导**。

## 3. 存储方案（二选一）

### 方案 A：新增 `keys.last_used_at` 列（推荐）

- v11 迁移（v10 已被 `backend_enabled` 占用），可空、无回填。
  历史调用没有逐 key 留时刻，回填不出来，NULL 即「从未使用」。
- **写入零额外开销**：`keys_dirty` 已经因为 `usage.count` 每次请求都置位，
  走的是同一条 5 秒防抖 flush。新增一个 int 赋值不增加任何落库次数。
- **写入集中在一处**：放在 `Store.check_api` 返回 `kid` 之前（§2 的定义直接对应
  鉴权成功那一刻），不需要碰 `pool.py` 的三个记账点。
- 秒级精度，能回答「现在还在用吗」。

### 方案 B：从 `key_usage_daily` 推算（零迁移）

`key_usage_daily(key_id, day, count, ...)` 已有每 key 每日计数，
「最后使用」= `MAX(day) WHERE count > 0`。

- ✅ 完全不需要迁移、不需要新列、不需要写。
- ❌ **天级精度**：答不了「上午 9 点还在用，下午 2 点就不用了」。
- ❌ **最多 5 秒滞后**，且跨天窗口更糟：`usage` 在本地 00:00 清零，
  刚过零点用过的 key 在首次 flush 之前仍显示昨天。
- ❌ 语义混淆：那是一张**每日快照**表（MAX 语义、故意只增不减），拿它推「最后使用」
  等于把一个非权威的聚合值当权威事实。

**推荐 A。** B 省掉的是一次迁移，换来的是精度与语义的正确性；而且写入本身是免费的。

## 4. 改动清单（按方案 A）

| 文件 | 改动 |
|---|---|
| `admin/db.py` | `_v10_to_v11` 迁移（`ALTER TABLE keys ADD COLUMN last_used_at INTEGER`）；`KEYS_DDL` 同步加列（**新库走 CREATE TABLE，不走 ALTER，漏了会 `no such column`**）；`KEY_COLUMNS` 加 `last_used_at`；`save_keys` 传值 |
| `admin/server.py` | `_load` 从 DB 行恢复 `last_used_at`；`check_api` 在返回 `kid` 前写入 |
| `admin/static/app.js` | 表格加「最后使用」列：有时间戳显示时间，无则显示「从未使用」 |
| `admin/static/index.html` | `<th>最后使用</th>` |

数据流向：DB → `_load` → `data["keys"][kid]["last_used_at"]` →
`check_api` 刷新 → `save_keys` 写回 → overview 的 `{k: v for k, v in item.items() if k != "hash"}`
自动透传 → 前端渲染。

## 6. 上一版的问题（为什么 revert 重做）

上一版做完了「加列 + 迁移 + 写入 + 展示」四条，但：

1. **`_load` 从没恢复 `last_used_at`** —— 每次重启内存里就没了，而
   `save_keys` 会把 `item.get("last_used_at")`（缺失 → None）写回 DB，
   **永久抹掉**。功能只在单次进程生命周期内有效。
2. **零测试**，所以上面这个 bug 没有任何东西能发现。
3. 混在总闸改动里一起提交，两者有 3 个文件重叠，边界不清。

另外记录一个环境事实：线上库当前是 **schema v9**，而 dev 分支已含 v10
（`backend_enabled`）。若要在线上验证这个功能，需先把总闸上线（v10）再上它（v11），
或一次性把两个迁移带上。

## 8. 排序与筛选

密钥总数是个位数到几十（不进 overview 全量返回，无分页），所以**前端排序筛选**即可，
不引入服务端参数。

### 8.1 筛选

沿用用量页 `usage-filter` 的 `<form>` + `<select>` 样式，放在密钥页工具栏下方：

| 选项 | 判定 |
|---|---|
| 全部密钥 | 不筛 |
| 今天用过 | `last_used_at >= 今日 00:00`（北京时间） |
| 超过 24 小时未用 | `last_used_at` 有值且早于 24 小时前 |
| 超过 7 天未用 | 同上，7 天 |
| 从未使用 | `last_used_at` 为空 |

这些**不是互斥分区**：「超过 7 天未用」是「超过 24 小时未用」的子集（两个都是
阈值查询，天然嵌套）。用户想要的是「多档里挑一档看」，不是「把 key 分进互斥的桶」，
所以嵌套在这里是对的——真要做互斥分区得改成一个「闲置天数」数值选择器，
而那个精度取决于用户记不记得上次用是几天前，反而不如阈值直接。

可以断言的是：任一 key 至少落在**一个**筛选里（今天用过 / 超过 24 小时未用 /
超过 7 天未用 / 从未使用 这四档覆盖全部情形），不会有关键词在四档里都漏掉。

**筛选与排序可叠加**，筛选在前、排序在后。

### 8.2 排序

表头可点击切换升 / 降。参与排序的列：

| 列 | 比较方式 |
|---|---|
| 名称 | 字符串（`localeCompare`） |
| 今日用量 | `usage.count`，缺失视 0 |
| 最后使用 | `last_used_at`，缺失视 0 |
| 创建时间 | `created` |

**默认不排序**——保持现有的插入顺序，不因新增一列就悄悄改变既有顺序。

### 8.3 NULL 的排序规则（最容易漏的一条）

`last_used_at` 为空的行（「从未使用」）**无论升序还是降序，一律排在最后**。

理由：升序时 `0` 天然会排到最前，看起来像「最久没用的」——但「从未使用」和
「2024 年用过一次」不是一回事。前者更值得被注意到（一个从没被用过的密钥可能是
配错的），却不代表它比「一年前还在用」更该保留。混排会让管理员误判清理优先级。

降序时 NULL 天然在最后，无需额外处理；这条规则实质是**给升序补一个例外**。

732 passed（687 → 732）。四个变异全部被抓住：

| 变异 | 抓它的测试 |
|---|---|
| `_load` 不恢复 `last_used_at`（**上一版的真 bug**） | `test_survives_save_and_reload` + `test_never_used_survives_round_trip_as_null` |

| DDL 漏改（只改 `KEY_COLUMNS`） | `test_fresh_database_has_the_column` |

实现过程中自己引入并修掉的两个问题：

1. **`_to_int(None)` 返回 0**，最初直接用它写 `last_used_at`，会把「从未使用」
   写成 `0`（1970 年）。改为原样传值。NULL 必须保持 NULL——前端按真值判断显示
   「从未使用」，而将来的「早于某时间」比较依赖 0 与 NULL 可区分。
2. 测试最初用构造函数的 `initial_key` 调 `check_api`，落在 `test_keys` 分支——
   那个分支不做可用性检查也不看配额，直接 `return None`，429 / 撤销这些分支
   根本走不到。**测试会假绿**。改用 `add_key` 返回的明文。

另修正文档一处过度声明：§8.1 原写「今天用过 / 超过 N 天未用互斥且覆盖全部情形」，
实测 `stale-1d ⊂ stale-7d` 是嵌套而非互斥，已改为准确表述。
