## 需求 1 · 积分 / token 整数显示

**现状**（实测线上数据）：
```
哈维        workbuddy   remaining=7596.5
AI 前沿     workbuddy   remaining=2088.33
15882308279 workbuddy   remaining=1777.98
Harvey      trae        remaining=4497.67
```
确实带小数。前端统一走 `creditsFmt`（`app.js:3-8`）：`Math.round(n*100)/100` + `maximumFractionDigits:2`。

**改法**：改一处 `creditsFmt` 即可覆盖账号池/概览/最早过期/日耗等**全部**积分显示点（`app.js:83,141,152,195-198`）。另需处理：
- `app.js:750,752,771,782` 用量报表（`maximumFractionDigits:2` / `toFixed(3)` 付费条均）
- `app.js:137` 成功率 `toFixed(1)` —— **这不是积分，是否也整数化要看 Q1**

**关键选择**：显示层取整 vs 存储层取整。
- 只改显示：`7596.5 → 7597`（四舍五入），DB 仍存 `_micro` 精确值，**不丢精度**，改动最小。**推荐。**
- 也改存储：破坏 `*_micro` 约定（schema v7 既有），且积分消耗对账会失真。**不推荐。**

**不确定**：
- 取整方式：四舍五入 / 向下取整 / 直接截断？（`4497.67` → `4498` or `4497`）
- 「日耗约」「预计过期浪费」这些**估算值**也整数化吗？估算值整数化会让「按当前速率约 N 天用完」跳变更明显。
- 总量（`7596.5+2088.33+...`）是**先求和再取整**，还是**各项取整再求和**？前者更准（推荐）。

## 需求 2 · 多后端架构重新设计 ⚠️ 最大的一块

**现状**：`BackendSpec`（`core/backends/base.py`）已是抽象层，`registry.py` 按**模型名前缀**路由。但 backend 名**硬编码渗透**在 ~15 处：

| 位置 | 硬编码内容 |
|---|---|
| `pool.py:635` | `if status == 404 and backend == "trae"` 软冷却 |
| `pool.py:745` | `if ... == "trae": return self._operate_trae(...)` 分派 |
| `pool.py:905` | `in ("workbuddy","trae")` 自动签到筛选 |
| `server.py:279` | `if backend not in ("workbuddy","trae")` 白名单 |
| `server.py:399/407` | `any_enabled_manager` / `any_trae_manager` 两个专用函数 |
| `server.py:698` | stale catalog 排除 trae |
| `server.py:1787` | test_model 检查 trae 账号存在 |
| `models.py:46` + `108-150,347-477` | 整个 trae 目录管理（前缀分支） |
| `app.js:131,141,152,198` | 前端 trae 徽标/积分分组 |
| `rotation.py:61` | `KNOWN_BACKENDS = ("workbuddy","trae")` |

**你的目标**：「后续还可以增加其他账号类型，如阿里千问办公」→ 加第三个后端时**不该再改这些地方**。

**改法（推荐分层做）**：
1. **后端能力声明化**：把「404 软冷却时长」「签到方式」「错误码解释」等从 `if backend==` 挪进 `BackendSpec` 的方法/属性。加新后端 = 新增一个类 + 注册，**零改动** pool/server。
2. **`make_credential` 补进基类**（现在没在 `base.py` 声明，是隐性契约）。
3. **前端后端元数据来自 API**：`GET /admin/api/backends` 返回 `[{name,label,icon,color}]`，前端不再写死 `"trae"`。
4. **`KNOWN_BACKENDS` 从注册表推导**，不再手写元组。

**代价**：触及 pool/server/models/前端共 ~10 文件。**收益**：需求 5/7 的 icon、需求 3 的 backend 字段都变成「读注册表」。

**不确定（Q2，重要）**：
- 这轮做到哪一步？**A. 只做「能力声明化 + 注册表驱动」**（不动 UI，为后续铺路）；**B. 连 UI 多后端化一起做**（含 Q4/Q6 的页面重构）；**C. 只修 bug 不重构**。
- 是否要为「阿里千问办公」**现在就预留**第三个后端骨架？还是只保证「将来加得动」？

## 需求 3 · 最近请求改造

**现状**：`request_logs` 表（`db.py:311-316`）**没有 backend 列**。UI 列是「来源 / 接口」= `source`(`api`/`test`) + `path`。默认每页 **50**，选项 50/100/200。

**改法**：
- schema v8：`request_logs` 加 `backend TEXT` 列（迁移时按 `account_id` 回填历史），写入点在 `pool.py:1264-1269` 的 `log_context` 补 `backend`。
- UI：把「来源 / 接口」列换成 **backend 徽标 + API Key 名称**（这是需求 3 要的「其他账号请求都要加入 + api key + 区分 trae/workbuddy」）。
- 默认 10 条，选项 **10/20/30/50**（改 `index.html:19` 下拉 + `loadLogs` 默认值）。

**不确定（Q3）**：
- 「不显示来源 / 接口」= 删掉这列，还是换成 backend+key 列？我理解是**后者**（because 下一句就要加 api key 和 backend 字段）。请确认。

## 需求 4 · 点 API Key 查看其最近请求

**现状**：`request_logs.key_id` 列**已存在**且有 `idx_logs_key_time` 索引（`db.py:332`），但 `page_request_logs` **不支持 key_id 过滤**，也无比 UI。

**改法**：小改。`page_request_logs` 加 `key_id` 参数 → `/admin/api/logs?key_id=` → API 密钥页点「今日用量」或新增「请求」按钮 → 弹框复用 `#dash-recent-body` 的渲染逻辑。**几乎零风险。**

## 需求 7 · API 密钥页优化

**现状**：分配策略是**内联 `<select>`**（`app.js:103`），无 icon，无独立设置按钮；模型/账号白名单走「权限」弹框。

## 需求 8 · 模型管理 ⚠️ 与需求 1 冲突

**实测线上重名（7 个）**：

| 模型 | workbuddy 倍率/ctx | trae 倍率/ctx |
|---|---|---|
| `deepseek-v4.1-flash` | **0.11** / 1000K | **0.06** / 200K |
| `glm-5.2` | **0.79** / 1000K | **0.78** / 200K |
| `glm-5.3` | **0.79** / 1000K | **0.78** / 200K |
| `glm-5.3-flash` | 0.06 / 1000K | 0.06 / 200K |
| `kimi-k2.6` | **0.52** / 256K | **0.75** / 200K |
| `minimax-m3` | **0.25** / 512K | **0.26** / 200K |
| `step-5-preview` | **0.0** / 1000K | **0.48** / 200K |

**冲突点**：
1. 你说「模型一样就显示一个」——但**倍率和上下文全都不同**（你这句后半段也说「不一致就 / 隔开」，两句是矛盾的：合并显示一个 + 显示不一致的值）。
2. 你说「批量禁用、启用」——**合并成一行后，禁用是禁两个还是一个**？`glm-5.3` 在腾讯是 0.79、字节是 0.78，很可能你只想禁掉便宜的那个。
3. 与需求 1 冲突：`step-5-preview` 腾讯侧倍率 = **0.0（免费）**，字节 = **0.48**。合并后这一个模型既是免费又是付费——**成本账本和排队降级都依赖倍率判定**，合并会丢信息。

**不确定（Q5，必须你定）**：
- 合并是**纯展示分组**（一行 + 展开看两后端），底层仍是两个独立模型？**（推荐——保留倍率差异与独立禁用）**
- 还是**真合并成一个模型**（调用时自动选便宜的后端）？**（会改变路由语义，风险高）**
- 批量禁用的粒度：**按键还是按该名字在两个后端都禁**？
- 用户级：**用户能看到"这个模型走哪条链路"吗？** 还是完全透明？

```
  ├─ schema v8: request_logs.backend
  ├─ 需求 3  最近请求列改造 + 分页 10/20/30/50
  └─ 需求 8a 模型管理合并显示（纯展示分组）+ 批量禁用

第 3 阶段（架构）——**已完成**（`1ef01e7`）

落地方式与预期一致：`BackendSpec` 成为唯一能力来源，registry 数据驱动，
调用方不再按后端名分支。两处计划外的收获：

- **架构守卫**（`tests/protocol/test_backend_arch_guard.py`）是这一阶段真正
  的交付物。行为测试**抓不住**这类回归：把软冷却、默认后端、账号操作分派
  改回按名分支，全量 640 条测试仍然全绿（作者做过变异验证）。「加后端零改动」
  只能靠结构守住，所以守卫扫源码，并把「前端自留元数据表」也一并钉死。
- **schema v9**：每个后端的「上次拉取时刻」原计划塞进 settings，但那张表是
  固定列的单行，后端数量可变就装不下（实测 `no such column: models_updated_trae`
  会挂掉整个 `create_app`）。改为记在 `models.synced_at` 上，加后端不动 schema。

登录方式按钮同时改为按 `login_kind` 渲染，`index.html` 不再写死后端名。

### 第 3 阶段的两轮 review（`68f335a`、`93d66a6`）

换了个模型做 review，两轮一共找出 4 条该修的，**都属于同一类病**：声称由声明
驱动、实际由字面量兜底或按名字分派，而且**行为测试全绿**。

| # | 问题 | 为什么测试抓不住 |
|---|---|---|
| 1 | `make_credential` 判据是「构造过没有」而非「是不是已知后端」 | 当前两个后端恰好都满足，懒构造的第三个才暴露 |
| 2 | `admin/pool.py` 顶部 `from core.backends.trae import ...` | 只在**冷启动**表现出「拖进整套私有协议」，进程内测试看不到 |
| 3 | 注册面散在四处：`known_names` 内建 order 字典、`default_name` 的字面量兜底、`spec_for` 的 `if name in ("trae",)`、`_load` 的按名分支 | 当年那张表的值恰好与硬编码一致 |
| 4 | `default_name()` 末尾 `return "workbuddy"` | 只有一个后端声明默认归属，兜底分支走不到 |

修法都不是「把那处改对」，而是**把差异挪进声明**：#1/#4 改为查注册表，
#2 新增 `error_class_name` + `upstream_error_class()` 与
`interpret_checkin_claim()`（都给声明、运行时取，避开「base 顶部 import 后端」
与「base 里为每个后端写转发方法」两种坏形状），#3 收敛成一张 `_REGISTRY` 表。

**最重要的产出是那几条新测试**。变异验证（11 处反模式）里，#3 和 #4 是
**先发现漏报、再补测试**的：把 `known_names` 的 order 改回硬编码字典
（`686 passed`）、把 `default_name` 改回字面量兜底（`684 passed`）全量都是绿的。
现在 `known_names` 的派生顺序、默认后端的声明归属、注册表条目的自洽性、
注册表里按名分支的处数（只允许 kill switch 与私有模型名映射两处）都有断言守着。

结论：**「零改动加后端」这条承诺无法用行为测试证明**（破坏它不影响任何现有行为），
只能靠源码扫描（arch guard，现 5 条规则）+ 结构断言（注册表派生、派生量跟着声明变）
一起钉死。

  ├─ 需求 2  后端注册表驱动 + 能力声明化 + /admin/api/backends
  ├─ 需求 5  账号类型 icon（读注册表）
  └─ 需求 6  页面合并（取消账号池页）
```

**每阶段独立可上线、独立回滚**，不必一次做完。

## 已确认决策（2026-10-15）

| 问题 | 决定 |
|---|---|
| **Q1** 整数化口径 | **向下取整（保守）**。只改显示层，DB 仍存精确 `*_micro`。 |
| **Q2** 需求 2 范围 | **A. 能力声明化 + 注册表驱动**。把 `if backend=="trae"` 挪进 `BackendSpec`；前端经 `/admin/api/backends` 拿元数据。加新后端 = 新增类 + 注册，pool/server 零改动。不动 UI 布局。 |
| **Q3** 需求 3 来源列 | **保留该列，精简为只显示 backend**（trae/workbuddy 徽标），不再显示 API/后台测试 与 path。 |
| **Q4** 需求 6 合并 | **概览内联完整账号表格**：搜索/筛选/批量签到都在概览，「账号工作区」升级为全表，点行开详情弹框；侧边栏移除「账号池」。 |
| **Q5** 需求 8 重名模型 | **合并显示 + 默认全选禁用/启用**：一行代表两后端，批量操作同时作用于两个后端。倍率/上下文不一致时用 `/` 隔开并列显示（保真，不丢免费/付费判定）。 |
| **Q6** 排期 | **按顺序全做，一次交一阶段**。每阶段独立可上线、可回滚，做完停下等验收。 |

### 由 Q5 决定的实现细节

- 合并后**不得**把两个后端的倍率合成一个数——`step-5-preview`（腾讯 0.0 / 字节 0.48）若合并，成本账本与排队降级会误判免费/付费。
- 展示形如：`×0.79 / ×0.78`（wb / trae），上下文 `1000K / 200K`。
- 批量禁用：选中一行 = 禁用该模型名的**全部后端**；如需单选后端，在展开区单独操作。
