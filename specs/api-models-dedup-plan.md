# `/v1/models` API 层去重（施工方案）

> 状态：**方案待确认，未编码**。用户 2026-10-16 拍板「做 (a)，生产发布暂缓」。
> 目标：把「用户只看到一个模型」从**只在管理页成立**，变成**在 API 客户端侧也成立**。

---

## 一、现状（实测）

dev `/v1/models` 返回 **42 条**：

| 类别 | 条数 | 例 |
|---|---|---|
| 带前缀 id | 22 | `trae/Doubao-Seed-2.1-Pro` |
| 裸名 id | 20 | `hy3`、`space-bunny` |

`kimi-k3` 相关返回 **两条**：`kimi-k3-1` 与 `trae/kimi-k3`。

也就是说：同一个模型（canonical 都是 `kimi-k3`）在 API 侧**出现两次**，客户端
（Cherry Studio、Open WebUI 等）会列成两个条目。用户得自己猜该选哪个 ——
这正是本轮要消灭的「把复杂度推给用户」。

**管理页没这个问题**：`groupModelsByName`（`app.js:288`）按 `canonical` 归组，
两行并成一行、倍率/上下文按后端分行展开。缺口只在 **API 输出层**。

---

## 二、目标与非目标

### 目标

1. 同一 `canonical` 的多个后端版本 → `/v1/models` **只返回一条裸名条目**。
2. 该条的 `owned_by` 写**当前策略第一名**（§9.6 已实现，复用即可）。
3. **带前缀 id 继续保留**（§6.2 原文），供高级用户显式指定后端。
4. 去重**不改路由**：路由看请求里的 `model` 字段，与列表无关。
5. 去重后返回的裸名 id **必须可路由且可被放行** —— 不能让客户端拿到一个
   「列表里有、请求却 400」的 id。

### 非目标（不改动）

- 不改 `model_id` / 前缀机制 / 账本键（§6.2 明确「不动」）。
- 不改管理页前端归组逻辑（已经是对的，读 `canonical`）。
- 不改 `enabled_models()` / `snapshot_ids()` 的**语义**（它们被请求路径的
  模型门与「禁用 vs 未知」判定复用，见 `pool.py:1378`）—— **去重只发生在
  `/v1/models` 的输出组装处**，不动这两个方法。
- 生产发布（用户拍板暂缓）。

## 三、关键设计决策（待你确认的有 3 个）

### D1. 裸名条目用「哪个 id」？

**决策：用该组内**默认后端**的裸名；默认后端没有该模型时，回落到组内排序第一名的裸名。**

理由：
- 裸名是最短、最中性的形式，且**不指向任何后端** —— 正是「系统按策略选后端」
  这个契约的对外表达。
- 但不能随便挑一个裸名。反例：`kimi-k3` 组里有腾讯 `kimi-k3-1` 与字节
  `trae/kimi-k3`。若挑中 `kimi-k3-1`，客户端传这个 id 上来，
  `canonical_name("kimi-k3-1") == "kimi-k3"` 命中候选集 —— 能路由，但
  客户端看到的是**腾讯的上游 id**，语义上把「上游实现细节」泄漏给了用户。
- 默认后端的裸名才是「规范形态」：`kimi-k3`。

**待确认①**：这条回落规则（默认后端优先）你是否认可？还是「一律用组内第一名
的裸名」更简单？我倾向默认后端优先，因为它与 `canonical` 的默认定义（「剥前缀
即规范名」）天然一致。

### D2. 组内所有成员都带前缀时怎么办？

**决策：取组内排序第一名的裸名作为 id。**

场景：某模型只在字节有（腾讯没有），组里只有 `trae/xxx` 一条。此时
- 裸名 `xxx` 传给服务端 → `canonical_name("xxx") == "xxx"`，
  查候选集用 canonical 匹配，**能命中字节那条** → 可路由。✅
- 但前提是 `canonical_name("xxx")` 得等于该组的 key。

**这里有个真实风险**（见 §四.R1）：若腾讯声明了 `kimi-k3-1 → kimi-k3`，
而字节那条的 canonical 来自剥前缀，那么「裸名 = canonical」在**声明过映射的
后端**上不成立。需要验证每个组的裸名确实能路由。

**待确认②**：如果某个组的「自然裸名」无法路由（极端情形），是
（a）干脆不返回这条裸名条目（只留带前缀行），还是（b）照返回、接受客户端
可能 400？我倾向 (a)：列表里的 id 必须可信。这个分支要在实现时用断言测出来。

### D3. `owned_by` 与 `created` 保持不变？

**决策：`owned_by` 沿用 §9.6 的 `_owner_backend_for`；`created` 保持假时间戳不动。**

`created` 是既有行为，与去重无关，动它属于范围外。

## 四、风险与验证点

### R1（高）裸名 id 的可路由性 —— 必须有测试兜底

去重后返回的每个裸名 id，都要满足两个条件，否则就是「列表骗人」：

1. `canonical_name(id)` 能命中至少一个后端候选（`bare_name_candidates` 非空）；
2. 该 id 能通过 `pool.py:1378` 的模型门（即 `id in enabled_models()`
   或**不在** `snapshot_ids()`）。

条件 2 尤其要注意：`enabled_models()` 返回的是**带前缀**的 id 列表
（`out += [prefix + mid ...]`）。裸名 `kimi-k3` **不在**其中 —— 但它在
`snapshot_ids()` 里吗？也**不在**（同样是带前缀的）。

→ 所以模型门那句 `model not in enabled_models() and model in snapshot_ids()`
对裸名 `kimi-k3` 是 `True and False == False` —— **不拦**。✅ 安全。
**但这条推理必须写成测试**，因为它是「为什么裸名请求今天不被误判为禁用」
的隐含前提，改动 `enabled_models` 时会悄悄失效。

### R2（中）前缀条目的 `owned_by` 不要被策略覆盖

`_owner_backend_for` 已经做了这个区分（`prefix_for(model)` 非空 → 走
`backend_name_for`）。去重不得破坏它 —— 带前缀行保留原 `owned_by`。

### R3（中）kill switch 关掉时

`bare_name_routing=False` 时裸名走默认后端。列表**仍然要去重**（去重是展示
层的事，与路由开关无关）。否则一关开关列表又变成 42 条，用户会以为是 bug。

→ 测试：关掉 kill switch，列表条数不变。

### R4（低）registry 未加载 / 目录为空

`get_available_models()` 可能回落到 `DEFAULT_MODELS`（硬编码列表，全裸名）。
此时去重应按 canonical 归组，`DEFAULT_MODELS` 里没有重名 → 条数不变。要确认
不崩。

### R5（低）同 canonical 但只有一个后端

单条组 → 原样透传，不合成。避免「本来好好的条目被改名」。

## 五、实现分解（3 个提交，各自独立可回滚）

### 提交 1：纯函数去重（不接线）

新增 `core/models_dedup.py`（或放 `core/bare_routing.py` 旁边，取决于你偏好）：

```python
def dedup_for_api(rows: list[dict]) -> list[dict]:
    """把「(id, backend, canonical)」行按 canonical 归并成 API 输出的 id 列表。

    输入是**已排序**的行（顺序 = 客户端看到的顺序），输出保持首现顺序。
    带前缀行**原样保留**；同 canonical 的多条裸名/带前缀行 →
    另出一条裸名条目（规则见方案 D1/D2）。
    """
```

**可测性**：输入输出都是纯数据，22 条单测覆盖 D1/D2/R5 各分支。

### 提交 2：接线 + 可路由性断言

- `converter.list_models` 在组装 `data` 前调 `dedup_for_api`。
- 数据源：`get_available_models()` 现在只给 **id 字符串列表**，拿不到
  `canonical`。需要拿到带 canonical 的行 —— **两个选项**：
  - **(i)** 让 `_managed_models` 顺带暴露 snapshot（多一次现算，但数据源唯一）；
  - **(ii)** 在 `list_models` 里对每个 id 调 `canonical_name(id)` 现算
    （与 `snapshot()` 同源同函数，无第二份真相）。

  我倾向 **(ii)**：`canonical_name` 就是「唯一判定处」，现算不引入新状态，
  且 `DEFAULT_MODELS` 回落路径也自然覆盖。**待确认③**：你选哪个？

- 加断言（测试里）：去重后每个裸名 id 满足 §四.R1 的两个条件。

### 提交 3：测试 + 文档

- `tests/protocol/test_models_dedup.py`：端到端，含
  - 42 → 期望条数（先在 dev 实测出准确数）；
  - `kimi-k3` 组只出裸名一条 + 带前缀 `trae/kimi-k3` 一条；
  - `owned_by` 正确；
  - kill switch 关掉条数不变（R3）；
  - 裸名 id 可路由（R1）。
- arch guard 补 `startswith("trae")` 规则（§6.3 的 (c)，顺手一起做）。
